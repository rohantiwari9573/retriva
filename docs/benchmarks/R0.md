# R0 baseline measurements

Local measurements taken on 2026-11-06. **None of this is production performance.**

- **Machine:** Windows 11, 12 logical CPUs, 16 GB RAM, Docker Desktop with 7.6 GB.
  Other containers were running, and the machine came under memory pressure later on.
- **Stack:** `docker-compose.isolated.yml`: one uvicorn process, one Celery worker, local
  Postgres, Redis and MinIO. Tracing off.
- **Embeddings:** a stub that responds instantly, so ingestion figures exclude real
  embedding latency. Real providers were not measured.
- **Load:** generated inside the backend container, so client and server share CPU.
  Latencies under concurrency include queueing in that one process.
- **Limits raised** so the limiter isn't what's measured. Each run adds to the same
  database only within a run; every run started on empty volumes.
- **Tool:** `backend/scripts/baseline_benchmark.py`.

## How far the comparison can be trusted

The "after" runs looked about 30% slower than the first "before" runs, including
`GET /health` and direct Redis calls, which this phase's code doesn't touch on those
paths. So one more run of the **old** code was taken afterwards ("before, later"). It
shows the same slowdown, so most of the gap came from the machine's state, not the code.

That's only one interleaved run, because the alternating series was stopped by the
system for low memory. **It supports "no large regression"; it can't show there's no
small one.** Retrieval is the one to watch: 143 ms on the old code against 165 and 172 ms
on the new. It's within this setup's noise, but a real small cost is possible, since
each limited request now runs a Lua script rather than plain `INCR`.

**Raw "after" JSON wasn't kept.** The stopped benchmark script kept running in the
background and overwrote those files while other work was under way. The "after" columns
are transcribed from the comparison output printed before that happened, and the
overwritten files were deleted rather than used. The "before" files are the originals.

## Database queries, `EXPLAIN ANALYZE`

Median execution time of 7 runs, 683 chunks in one tenant ("Before 1").

| Query | Execution | Rows returned | Plan |
|---|---|---|---|
| Document list | 0.019 ms | 20 of 20 | Seq scan (small table) |
| Keyword search | 0.817 ms | 20 of 20 | Seq scan |
| Vector search | 0.055 ms | **7 of 20** | IVFFlat index scan |

**The vector result is a defect, not a fast query.** The planner chose the IVFFlat index,
which was built on an empty table and by default scans one list, so most chunks are never
looked at. Rows were 7, 7, 8 and 7 across the runs that recorded them. Retrieval currently
returns incomplete results with no error. This is scheduled for R4 and unchanged by R0.

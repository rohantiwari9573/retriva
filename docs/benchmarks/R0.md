# R0 measurements

**Exploratory evidence, not statistically conclusive.** The approved two-round comparison of
the original code, R0, and R0 with the vector fix finished 5 of its 6 runs. Its memory
guard stopped it during the original code's second round. **None of this is production
performance.**

## Two-round comparison, 2026-11-09

`controlled/run-20261109T151350Z/`. All three versions ran with the same Compose files,
the same `pgsty/minio` image, the same 23 documents and 683 chunks, and the same workload.
Nothing else was running. Raw JSON for every completed run is in that folder;
`status.json` records the stop.

| Version | Commit | Round 1 | Round 2 |
|---|---|---|---|
| Original | `f60c34c` (`master`) | Complete | Ingestion and cold only: stopped at 0.72 GB free |
| R0 | `5239f1e` | Complete | Complete |
| R0 and vector fix | `e688d17`, a local merge that wasn't pushed | Complete | Complete |

Error rate was 0% in every completed run.

**p50 latency in ms, cold then warm.** Each cell lists round 1, then round 2.

| Endpoint | Original | R0 | R0 and vector fix |
|---|---|---|---|
| `GET /health` | 101, 93 / 112, none | 77, 92 / 108, 87 | 81, 77 / 75, 98 |
| `GET /readiness` | 80, 67 / 74, none | 66, 76 / 78, 65 | 62, 79 / 67, 79 |
| Login, correct | 226, 238 / 233, none | 248, 257 / 289, 275 | 273, 276 / 264, 283 |
| Login, wrong password | 235, 235 / 223, none | 274, 236 / 267, 260 | 249, 251 / 235, 240 |
| `GET /documents` | 64, 68 / 91, none | 81, 60 / 69, 68 | 61, 64 / 60, 64 |
| Hybrid retrieval | 122, 130 / 129, none | 132, 120 / 126, 113 | 110, 135 / 126, 126 |

Mean, p95, p99 and requests per second are in each `*-2-cold.json` and `*-3-warm.json`.

- **Correct logins look slower with R0**, by about 10 to 60 ms at p50, in all eight
  runs that include R0. That fits the account limiter's extra Redis calls. It's small, but consistent.
- **Other endpoints overlap** between versions, run to run.
- **Large-document ingestion was faster with R0:** p50 of 458 to 474 ms against 540 to
  560 ms. R0 doesn't change ingestion, and this isn't explained, so don't read it as an
  improvement.

**Vector retrieval compared with exact search, top 30, 20 queries:**

| | Rows returned | Recall |
|---|---|---|
| Original | 6.85 to 7.3 | 1.5% to 2.2% |
| R0 | 6.5 to 6.7 | 1.8% |
| R0 and vector fix | **30** | **100%** |

These are random stub vectors, the worst case for the index. MRR with a real embedding
model is in the vector fix's evaluation, not here.

**CPU and memory, warm runs.** The API container peaked at 250 to 300% CPU in every version
and at 160 to 225 MB of memory, with Postgres at 92 to 102 MB. Samples are taken every 5 s,
5 to 7 per run, so they're coarse. Ingestion finishes in under 8 s, so it got one sample or
none: treat ingestion CPU and memory as not measured.

**An earlier attempt on 2026-11-06,** `controlled/run-20261106T175730Z/`, also completed 5
of 6 runs. The session running it ended, so its `status.json` was written by hand.

An earlier version of this document said every run started on empty volumes. That was
wrong: Before 2 and After 2 each reused the previous run's database. So those runs aren't
equivalent to the others, and their vector-search and document-list figures aren't directly
comparable.

**What can't be concluded:** whether R0 has a small effect on normal request latency. The
one finding is that the earlier apparent 30% slowdown also appeared in the old code when
re-run later, so most of it came from the machine's state. It's one run, with different
background load from the others.

## Original code, controlled conditions

guard didn't trigger. One round only, so there's no measure of spread. Error rate was 0%
everywhere.

| `GET /readiness` (500, 10) | 73 / 57 / 151 / 228 | 84 / 77 / 159 / 250 | 136 / 119 |

Warm isn't consistently faster than cold here. A single round can't separate cache effects
from noise.

| Other measurements | Cold | Warm |
|---|---|---|
| Redis `INCR`, p50 / p99 | 0.08 / 0.27 ms | 0.12 / 0.47 ms |
| Keyword search, median of 7 | 0.88 ms | 1.22 ms |
| Vector search, median of 7 | 0.07 ms, **9 of 20 rows** | 0.13 ms, **9 of 20 rows** |
| **Vector retrieval vs exact, top 30, 20 queries** | **6.95 rows on average, recall 1.2%** | **6.95 rows, recall 1.2%** |

The fast vector time is because of the defect: it's searching about 1% of the table. These
vectors are random, a worst case for this index: see
[the vector fix's measurements](https://github.com/rohantiwari9573/retriva/pull/2).

**Ingestion, upload through READY, stub embeddings, all READY:**

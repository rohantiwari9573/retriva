# R0 measurements

**There's no complete before-and-after comparison yet.** The controlled run was stopped by
the system for low memory, after finishing one of nine variant runs. What exists is below,
with the conditions of each set. **None of this is production performance.**

**Machine for everything here:** Windows 11, 12 logical CPUs, 16 GB RAM, Docker 29.4 with a
7.6 GB VM. See [METHODOLOGY.md](METHODOLOGY.md) for the method and its limits.

## What was measured, and under what conditions

| Set | Code | Data state | Other containers | Raw data | Trust |
|---|---|---|---|---|---|
| Before 1 | Original | Empty volumes, then **23 documents, 683 chunks** | Your Retriva stack | `r0-before-run1.json` | Original file |
| Before 2 | Original | **Reused Before 1's database: 46 documents, 1,366 chunks** | Your Retriva stack | `r0-before-run2.json` | Original file |
| Before, later | Original | Fresh, 23 documents | Your stack, plus memory pressure | `r0-before-interleaved.json` | Original file |
| After 1 | R0, older commit | Fresh, 23 documents | Your stack and test containers | **Lost** | Transcribed from printed output |
| After 2 | R0, older commit | Reused After 1's database, 46 documents | Same | **Lost** | Transcribed from printed output |
| Controlled, round 1 | Original | Fresh, 23 documents, 683 chunks | **None** | `controlled/run-20261106T094017Z/` | Original files, cold and warm separated |

An earlier version of this document said every run started on empty volumes. That was
wrong: Before 2 and After 2 each reused the previous run's database. So those runs aren't
equivalent to the others, and their vector-search and document-list figures aren't directly
comparable.

**What can't be concluded:** whether R0 has a small effect on normal request latency. The
one finding is that the earlier apparent 30% slowdown also appeared in the old code when
re-run later, so most of it came from the machine's state. It's one run, with different
background load from the others.

## Original code, controlled conditions

From `controlled/run-20261106T094017Z`, round 1. Nothing else was running, and the memory
guard didn't trigger. One round only, so there's no measure of spread. Error rate was 0%
everywhere.

| Endpoint (requests, concurrency) | Cold: mean / p50 / p95 / p99 ms | Warm: mean / p50 / p95 / p99 ms | Requests per second, cold / warm |
|---|---|---|---|
| `GET /health` (2000, 20) | 140 / 85 / 438 / 801 | 162 / 99 / 520 / 828 | 142 / 123 |
| `GET /readiness` (500, 10) | 73 / 57 / 151 / 228 | 84 / 77 / 159 / 250 | 136 / 119 |
| Login, correct (100, 4) | 242 / 236 / 297 / 322 | 254 / 246 / 351 / 451 | 16.4 / 15.6 |
| Login, wrong password (100, 4) | 241 / 234 / 294 / 321 | 243 / 241 / 272 / 281 | 16.5 / 16.3 |
| `GET /documents` (500, 10) | 87 / 67 / 214 / 453 | 84 / 60 / 231 / 406 | 114 / 118 |
| Hybrid retrieval (200, 4) | 116 / 105 / 175 / 221 | 126 / 127 / 172 / 197 | 34.5 / 31.3 |

Warm isn't consistently faster than cold here. A single round can't separate cache effects
from noise.

| Other measurements | Cold | Warm |
|---|---|---|
| Redis `INCR`, p50 / p99 | 0.08 / 0.27 ms | 0.12 / 0.47 ms |
| Keyword search, median of 7 | 0.88 ms | 1.22 ms |
| Vector search, median of 7 | 0.07 ms, **9 of 20 rows** | 0.13 ms, **9 of 20 rows** |
| **Vector retrieval vs exact, top 30, 20 queries** | **6.95 rows on average, recall 1.2%** | **6.95 rows, recall 1.2%** |

The fast vector time is because of the defect: it's searching about 1% of the table. These
vectors are random, a worst case for this index: see
[the vector fix's measurements](https://github.com/rohantiwari9573/retriva/pull/2).

**Ingestion, upload through READY, stub embeddings, all READY:**

| Document | Original: mean / p50 / p95 ms | R0: mean / p50 / p95 ms |
|---|---|---|
| 4 KB, 3 chunks, 20 documents | 110 / 94 / 105 | 106 / 89 / 113 |
| 400 KB, 208 chunks, 3 documents | 588 / 537 / 708 | 578 / 527 / 690 |

From one round each, and the only like-for-like comparison available. It shows no sign of a
difference, which is expected, since R0 doesn't change ingestion.

**CPU and memory weren't captured.** A bug in the runner left those fields empty. It's fixed,
and a re-run would record them.
